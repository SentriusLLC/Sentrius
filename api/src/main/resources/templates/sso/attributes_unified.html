Attribute-Based Access Control (ABAC)

Understanding ABAC in Sentrius

Attribute-Based Access Control (ABAC) provides fine-grained access control by evaluating attributes of users, resources, actions, and the environment. Sentrius implements ABAC through four key components:

1. Attribute Definitions: Define the schema for attributes (e.g., department, clearance_level) that can be assigned to users, resources, or other entities.

2. User Assignments: Assign specific attribute values to users (e.g., user "john.doe" has department=engineering). These can be synced from Keycloak or managed locally.

3. Access Mappings: Simple rules defining which attribute values are required to access specific endpoints (e.g., /api/v1/chat/** requires department=engineering).

4. Access Policies: Advanced rule-based policies with complex conditions, operators, and UI control support. Perfect for controlling menu visibility and sophisticated access scenarios.

📋 How to Use ABAC - Step by Step
Step 1: Go to Attribute Definitions tab and create an attribute (e.g., department with type STRING)
Step 2: Go to User Assignments tab and assign values to users (e.g., assign department=engineering to user "john.doe")
Step 3a: For simple API access: Go to Access Mappings tab and create rules (e.g., require department=engineering to access /api/v1/chat/**)
Step 3b: For UI control or advanced rules: Go to Access Policies tab and create policies with complex conditions (e.g., control who sees AI Services menu)
💡 UI Control Example: Create a policy for /ui/ai/services requiring team=ai. Enable enableAbacUiControl in System Settings to dynamically show/hide menu items based on user attributes.

Attribute Definitions
📝 Step 1: About Attribute Definitions
Define attribute schemas that can be used across the ABAC system. Attributes can apply to subjects (users, roles), resources (endpoints, data), actions (operations), or environment (context).

Example: Create a department attribute of type STRING with scope SUBJECT. This allows you to track which department each user belongs to.

Access Mappings
🔒 Step 3: About Access Mappings
Define attribute requirements for accessing specific endpoints. This enables fine-grained access control based on user properties. This is where you enforce the rules!

Example: Create a mapping for endpoint /api/v1/chat/** requiring department=engineering. Now only users with department=engineering (like john.doe) can access the chat API, while users with other departments (like jane.smith with finance) will be denied.

Access Policies
🛡️ Step 4: About Access Policies (Advanced ABAC)
Access Policies provide advanced, rule-based access control with support for complex conditions, multiple attributes, and logical operators. Use this for UI element control and sophisticated access scenarios.

Key Differences from Access Mappings:
  • Access Mappings: Simple endpoint + single attribute/value check
  • Access Policies: Complex rules with AND/OR logic, operators (EQUALS, CONTAINS, GREATER_THAN, etc.), and UI control
UI Control Example: Create a policy for /ui/ai/services with rule team EQUALS ai. When enableAbacUiControl=true in System Settings, only users with team=ai will see the AI Services menu item.
